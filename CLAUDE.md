# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A seating chart / classroom management app with two independent halves that run as separate processes:

- **Frontend** (repo root): React Router 8 (framework mode, SSR) + Tailwind CSS v4 + shadcn (`base-rhea` style, via `@base-ui/react`), served from `app/`.
- **Backend** (`src/`, repo root): Rust Axum API backed by Supabase Postgres via `tokio-postgres` + `deadpool-postgres`, serving JSON at `/api/v1/*` on port 3001. There is no Cargo workspace — the crate lives directly at the repo root, alongside the frontend's `app/`.

The frontend calls the backend directly over HTTP at hardcoded `http://localhost:3001` URLs, all funneled through `app/lib/api.ts` — there is no shared client/server code or generated API types between the two halves, so `app/lib/types.ts`/`app/lib/schemas.ts` (frontend) and `model.rs`/`schema.rs` (backend) must be kept in sync manually when the API shape changes.

## Installed skills

Four Claude Code skills are relevant to this project: `react-router`, `shadcn`, `neon`, and `neon-postgres`. These are installed globally (user scope, available across all projects, not tracked in this repo) rather than project-locally. All auto-trigger on their respective topics, so no manual invocation is needed — but be aware they exist and take precedence over prior/general knowledge:

- **react-router** — this app is Framework Mode (`@react-router/dev`, SSR, `app/routes.ts`-based routing per the Frontend architecture section below); load the Framework Mode reference specifically, not Data/Declarative/RSC mode guidance.
- **shadcn** — this app uses the `base-rhea` style on Base UI (see the shadcn bullet in Frontend architecture below); use the skill's CLI commands (`npx shadcn@latest ...`) to add/update components rather than hand-writing them, and check `npx shadcn@latest info --json` for current project/component state before assuming what's installed.
- **neon** / **neon-postgres** — the backend's Postgres database is hosted on Neon (see `.neon` for the linked project/branch); load these before using the Neon CLI or MCP server, or when touching connection/branching/pooling behavior, rather than assuming a generic Postgres host.

There is no lint script. Prettier is configured (`.prettierrc`: no semicolons, double quotes off/`singleQuote: false`, `prettier-plugin-tailwindcss` for class sorting) but not wired to an npm script — run `npx prettier --write .` directly if needed.

### Backend (run from repo root)

```bash
cargo run                                  # start the API server on 0.0.0.0:3001
cargo test --all-features                  # run tests (matches CI)
cargo clippy -- -D warnings                # lint (matches CI, warnings fail the build)
cargo fmt                                  # format
cargo fmt --check                          # format check (matches CI)
```

The backend reads one env var for the database: `POSTGRES_URL`. In Preview/Production it's injected by the Supabase Vercel integration and points at the Supabase **Supavisor transaction pooler** (`aws-*.pooler.supabase.com:6543`); for local dev `.env` sets it to the Supabase CLI's Postgres (`127.0.0.1:54322`, direct). There is no `DATABASE_URL` fallback.

The transaction pooler multiplexes client connections across shared backends per-transaction, so a server-side prepared statement created on one request can be gone (or collide) on the next. That is why the backend does **not** use `sqlx` (which always names prepared statements) and why nothing here uses compile-time query macros. Instead:

- **`src/db.rs`** is small: `Db = deadpool_postgres::Pool` + `build_pool` (strips Supabase's `?supa=...` URL param, connects TLS via `tokio-postgres-rustls` / aws-lc-rs / webpki roots). No query wrappers.
- Handlers get a connection with `let conn = data.db.get().await?;` then call `tokio_postgres` **directly**: `conn.query_typed(...)` / `conn.query_typed_one(...)` / `conn.query_typed_opt(...)` / `conn.execute_typed(...)`. These use the **unnamed** prepared statement in one round-trip — the only pooler-safe path. Never call `conn.query(...)` / `execute(...)` / `prepare(...)` (all named-statement).
- `query_typed*` takes `&[(&(dyn ToSql + Sync), Type)]` — an explicit `tokio_postgres::types::Type` per `$n` bind (`Type::TEXT` / `UUID` / `INT2` / `INT4` / `INT8` / `TIMESTAMPTZ` / `UUID_ARRAY`).
- Row → struct: `Model` derives `postgres_from_row::FromRow`; `Model::try_from_row(&row)?` for one, `rows.iter().map(Model::try_from_row).collect::<Result<Vec<_>, _>>()?` for many. Scalars: `row.get(0)` / `row.try_get("col")?`.
- Zero-rows → 404: `conn.query_typed_opt(...).await?.ok_or_else(|| not_found("Classroom"))?` (each of `classroom.rs`/`student.rs` has a local `not_found(&str) -> AppError`).
- `student_list_handler` builds its dynamic query as a `String` + `Vec<(&(dyn ToSql + Sync), Type)>` and passes both to `conn.query_typed`.
- The two multi-statement writes (`update_seating_chart_handler`, `update_student_handler`) use `conn.transaction()` and call the same `tx.query_typed*` / `tx.execute_typed` methods.
- `AppError` has `From<tokio_postgres::Error>` + `From<deadpool_postgres::PoolError>` (both → `Internal`), so `?` works on every `.await`.

No compile-time DB is needed: `cargo build`/`check`/`clippy` never touch a database. Only `cargo test` does (at runtime — see Testing). Migrations live in `supabase/migrations/*.sql` (one flat forward-only file; root `migrations/` is a symlink) and are applied to real environments out-of-band via the Supabase CLI / dashboard / MCP — `vercel.json`'s `buildCommand` is just `npm run build`.

## Architecture

### Backend (`src/`)

- `lib.rs` — the crate is a library with two thin binaries on top of it (`[[bin]]` entries in `Cargo.toml`): `src/main.rs` (local dev/docker-compose) and `api/index.rs` (Vercel Functions). `lib.rs` holds every `mod` declaration (including `pub mod db;`), `AppState { db: db::Db, blob_* }`, and `AppState::build()` — reads `POSTGRES_URL`/`S3_*` env vars, builds the `deadpool_postgres` pool via `db::build_pool` (max `MAX_CONNECTIONS`, kept low since Vercel Fluid Compute runs several instances each with their own pool against a small shared Supavisor pool size), health-checks it, and constructs the S3 blob deleter. Both bins call `AppState::build()` then `create_router(...)` — this is the one place that wiring lives, not duplicated per bin. `AppState`'s fields are private, so external bins can't construct it with struct-literal syntax even though they're part of the same package (bins depend on the lib crate rather than being inside it) — that's why `build()` exists as a constructor rather than assuming the spec's original "just construct it directly" shape.
- `main.rs` — local-dev entry point; loads `.env`, calls `AppState::build()`, builds the router, and serves on `0.0.0.0:3001`. Behaviorally identical to the pre-migration binary-only crate's `main.rs`.
- `../api/index.rs` (repo root, not under `src/`) — the Vercel Functions entry point: same `AppState::build()` + `create_router(...)` call as `main.rs`, but wrapped in `vercel_runtime`'s `VercelLayer` (`features = ["axum"]` on the `vercel_runtime` dependency) via `ServiceBuilder::new().layer(VercelLayer::new()).service(router)`, then handed to `vercel_runtime::run(...)` — no `TcpListener`, Vercel's runtime invokes the function through its own bridge. `vercel.json` rewrites `/api/v1/:path*` and `/health` to this function's bare path (`/api/index`) — the rewrite only picks *which* function serves a request, Vercel still forwards the original path, so the Axum router matches routes exactly as declared in `routes.rs` with no extra prefix-stripping needed.
- `routes.rs` — `create_router(app_state, clerk_layer, frontend_origin)` wires every `/api/v1/*` route (all take `Arc<AppState>` as shared state) plus a public `/health` route, CORS (scoped to `frontend_origin`), request tracing, and `log_app_errors` middleware. `clerk_layer` is `Some(...)` in production (verifies every `/api/v1/*` request's Bearer token) and `None` in tests (see Testing below).
- `auth.rs` — Clerk integration: `clerk_layer` builds the `ClerkLayer` used above (JWKS-verified, Bearer-token only, no session-cookie fallback), and the `CurrentUserId` extractor pulls the verified Clerk user id (`sub` claim) out of the request for handlers to scope queries by. Every `classrooms`/`students` row carries a `user_id`; handlers filter/insert by the extracted id so users only ever see their own data.
- `blob.rs` — `BlobDeleter`/`BlobReader`/`BlobUploader` traits for a student photo's full lifecycle against a real Cloudflare R2 bucket in every environment (a dedicated bucket per environment — dev/preview/production — no MinIO, including locally). Deletion is fire-and-forget (logged, never propagated as a handler error). Both photo reads and upload-presigning go through the Rust backend (`GET`/`POST` handlers in `handlers/student.rs`, see Frontend section) rather than the frontend talking to S3 directly, since presigning needs the S3 secret key server-side.
- `cold_call.rs` — pure, DB-free `pick_cold_call_student`: weighted-random pick from the caller-supplied `(student_id, weight)` list, then bumps every other candidate's weight by `WEIGHT_INCREMENT` so repeats become less likely. Weights are ephemeral, request-scoped state (not persisted) — the frontend owns them for the lifetime of a cold-call session. `POST /api/v1/classrooms/{classroom_id}/cold-call` (`cold_call_handler`, `classroom.rs`) is a thin wrapper, same pattern as `randomize_seating_chart_handler`.
- `handlers/` — one file per resource (`classroom.rs`, `student.rs`, `separation.rs`), each generally exposing `{resource}_list_handler`, `get_{resource}_handler`, `create_{resource}_handler`, `update_{resource}_handler`, `delete_{resource}_handler`. This CRUD-per-file pattern is the template for a new resource, but it's a default, not a requirement — tables/seats have no per-resource CRUD or dedicated handler file at all; they're only ever read/written as a unit via the seating-chart endpoints in `classroom.rs` (see below). There is no `table.rs`/`seat.rs` handler file and no tables/seats REST endpoint. `separation.rs` only exposes list/create/delete (`GET`/`POST /api/v1/separations`, `DELETE /api/v1/separations/{id}`) — a separation pair has no independent update, and `list_separations_handler` returns every one of the user's pairs unscoped by classroom (the frontend filters down to a given classroom's roster itself). `student.rs` also has two endpoints outside the standard per-id CRUD shape: `GET /api/v1/students/count` (returns `{count, limit}`, backing the frontend's limit-status UI) and a bulk `DELETE /api/v1/students` (body-driven multi-id delete, `bulk_delete_students_handler`).
- `model.rs` — `postgres_from_row::FromRow` structs (`ClassroomModel`, `StudentModel`, `StudentSeparationModel`, `TableModel`, `SeatModel`) mapping directly to DB rows. `TableModel`/`SeatModel` are only deserialized by test helpers (via `RETURNING *`/`SELECT *`); `get_seating_chart_handler`'s join query deserializes straight into `schema.rs`'s `TableSchema` (also `FromRow`) instead.
- `schema.rs` — separate `*Schema`/`Update*Schema` structs for request bodies (create takes required fields; update takes all-`Option` fields for partial updates, with a `deserialize_some` helper distinguishing "field omitted" from "field explicitly `null`" for nullable columns like `classroom_id`). `SeatingChartSchema`/`TableSchema` are the exception to the per-resource CRUD shape: they model the *entire* seating chart as one nested payload (`{ boundary_width, boundary_height, tables: [{ table_number, rows, cols, x_pos, y_pos, seat_assignments: [student_uuid | null, ...] }] }`), where a seat's position in the `seat_assignments` array *is* its `seat_number` column — there's no separate seat schema. `rows`/`cols` (each `CHECK`-constrained 1-15 in the DB) describe the table's seat grid shape; total seat count is `rows * cols`, and there's no separate `seat_count` column.
- Every table's primary key is `id UUID` directly (no separate internal numeric id); lookups by resource use this `uuid` in URL paths, e.g. `/api/v1/students/{uuid}`. Update handlers fetch the existing row first, merge in any provided fields over the existing values, then issue the `UPDATE`.
- Every handler returns `Result<impl IntoResponse, AppError>` (`error.rs`) rather than a raw tuple: `AppError` is a small enum (`NotFound`/`Internal`/`BadRequest`/`Unauthorized`, with `From<tokio_postgres::Error>` and `From<deadpool_postgres::PoolError>` both mapping to `Internal`; zero-rows → `NotFound` is done explicitly at the call site) whose own `IntoResponse` renders `{"message", "code"?, "retry_after_secs"?}` (the latter two are currently always omitted — reserved for future rate-limiting) and stashes itself in the response extensions so the `log_app_errors` middleware (`routes.rs`) can log it; only `NotFound`/`Internal` are logged as unexpected failures, since `BadRequest`/`Unauthorized` are routine caller-facing outcomes. Success responses are unchanged: an explicit `StatusCode` and a `{"data": ...}` envelope (no `"status"` field in the body — the HTTP status code carries that) — follow this shape for new handlers rather than introducing a new response convention.
- `seating_chart.rs` — pure, DB-free logic backing `POST /api/v1/classrooms/{classroom_id}/seating-chart/randomize` (`build_randomized_chart`, plus its own `TableGeometry` type and table-layout geometry constants: `GRID_STEP`, `TABLE_OFFSET`, `TABLE_GAP`, `SEAT_NODE_SIZE`, `SEAT_PADDING`). These constants are manually mirrored from `app/lib/seating-chart-utils.ts` so new-table placement matches the canvas's own grid convention — keep both sides in sync by hand. `build_randomized_chart` takes the caller's `boundary_width`/`boundary_height` and places any needed new tables via a row-major, `GRID_STEP`-increment scan (`find_new_table_position`) for the first spot that doesn't overlap an existing table (plus a `TABLE_GAP` margin); it returns `Err(SeatingChartError::NotEnoughRoom)` if no spot fits within the boundary, which `randomize_seating_chart_handler` maps to a `400 Bad Request`. `handlers/classroom.rs::randomize_seating_chart_handler` is otherwise a thin wrapper around this module: it validates the request, loads the student roster, and delegates the actual placement/shuffle to `build_randomized_chart`; `build_randomized_chart` also takes each student's optional `seating_preference` and makes a best-effort pass seating front/back-preferring students into the front/back-most rows before shuffling everyone else into the remaining seats at random.
- `classrooms.pinned_at` (`TIMESTAMPTZ`, nullable) is set/cleared via the normal `PATCH /api/v1/classrooms/{classroom_id}` partial-update merge (`update_classroom_handler`) — there's no dedicated pin/unpin endpoint. The backend enforces two per-user caps in `classroom.rs`: `MAX_CLASSROOMS_PER_USER` (50, checked in `create_classroom_handler`) and `MAX_PINNED_CLASSROOMS_PER_USER` (10, checked only on the unpinned→pinned transition in `update_classroom_handler`, so reordering or unpinning is never blocked). `app/lib/classroom-limit.ts` mirrors both caps client-side to disable the relevant UI proactively, but the backend check is authoritative — same "fails open" pattern as `MAX_STUDENTS_PER_USER` (850, `student.rs`) and `app/lib/student-limit.ts`.
- Every classroom has a `boundary_width`/`boundary_height` (pixel dimensions of its seating chart's canvas rectangle, DB defaults `1080`/`820`). The seating-chart `PUT` (`update_seating_chart_handler`) is the primary write path from the canvas Save flow — it persists `boundary_width`/`boundary_height` alongside the tables in the same transaction, so a single request saves both. `PATCH /api/v1/classrooms/{classroom_id}` (`update_classroom_handler`'s normal partial-update merge) still accepts boundary fields too and remains the write path for other callers (e.g. `ClassroomFormDialog`'s subject/period edits), but the seating-chart page no longer uses it. `create_classroom_handler`/`ClassroomSchema` don't accept boundary dimensions at all; a new classroom always starts at the DB defaults. `RandomizeSeatingChartSchema` carries the frontend's current (possibly unsaved) boundary size alongside `existing_tables`, for the same reason it carries table geometry — see below.

### Seating chart persistence (`GET`/`PUT /api/v1/classrooms/{classroom_id}/seating-chart`)

Tables and seats are **not** individually addressable via REST — the entire chart is read/written as one document, matching how the frontend canvas treats it as a single piece of state:

- `PUT` (`update_seating_chart_handler`, `classroom.rs`) is a full replace inside one transaction: update the classroom's `boundary_width`/`boundary_height` (404ing if the classroom doesn't exist), delete every `tables` row for the classroom (cascades to `seats`), then re-insert every table (assigning `table_number` from array index, storing the request's `rows`/`cols` as-is) and every seat (assigning `seat_number` from its index within that table's `seat_assignments` array, including empty seats as `NULL` `student_id` rows). There is no diffing — moving one table round-trips the whole chart. The handler is agnostic of how `seat_assignments`' flat index maps onto a `(row, col)` grid position — that row-major convention lives entirely on the frontend (see below).
- `GET` (`get_seating_chart_handler`) fetches the classroom's `boundary_width`/`boundary_height` (404ing if the classroom doesn't exist) and joins `tables`/`seats` to return each table's `rows`, `cols`, `x_pos`, `y_pos`, and a dense `seat_assignments` array (`ARRAY_AGG` ordered by `seat_number`, one entry per seat including unoccupied ones as `null`), ordered by `table_number`.
- `POST .../seating-chart/randomize` (`randomize_seating_chart_handler`) is the one exception to "read or write the whole chart": it never touches `tables`/`seats` at all (no transaction, no `INSERT`/`DELETE`), only reads `students` for the roster. It takes the *frontend's current in-memory table geometry and boundary* as part of the request body (not persisted state), proposes a full chart via `seating_chart::build_randomized_chart`, and echoes the request's boundary back alongside it in the same `SeatingChartSchema` shape as `GET`/`PUT` — the frontend applies it as an unsaved canvas edit, and only the normal `PUT` ever persists it.

### Database schema (`migrations/*.sql`, one numbered file per schema change)

Five tables, defined across four migrations: `classrooms`, `students`, `tables`, `seats` (`0001`), plus `student_separations` (`0004`). Students optionally reference a `classroom_id`; seats belong to tables (`ON DELETE CASCADE`) and optionally reference a student (`ON DELETE SET NULL`, `UNIQUE` — a student can occupy at most one seat); tables belong to classrooms. `classrooms.boundary_width`/`boundary_height` (`INTEGER`, defaulting to `1080`/`820`) are the seating chart canvas's boundary rectangle, in the same pixel units as `tables.x_pos`/`y_pos`. `tables.x_pos`/`y_pos` are canvas coordinates (integers, one `GRID_STEP` unit apart); `tables.rows`/`cols` (each `SMALLINT`, `CHECK`-constrained to 1-15) describe the table's seat grid shape — there's no `seat_count` column, since total seats is always `rows * cols`; `seats.seat_number` is a seat's index within its table's `seat_assignments` array, not a coordinate. `classrooms.user_id`/`students.user_id` (`TEXT`) hold the owning Clerk user id (see `auth.rs` above) for per-user scoping. `classrooms.pinned_at` (`TIMESTAMPTZ`, nullable, `0002`) drives classroom pinning (see above). `students.student_id` (`INTEGER`) is a roster number distinct from its `id` UUID. `students.image_url` (`TEXT`, nullable) points at the student's photo in blob storage (see `blob.rs`). `students.seating_preference` (`TEXT`, nullable, `0003`, `CHECK`-constrained to `'front'`/`'back'`) is a student's optional preferred seating row, used by `build_randomized_chart`. `student_separations` (`0004`) models a "keep these two students apart" constraint as one row per unordered pair: `student_id_a`/`student_id_b` (both `ON DELETE CASCADE`) plus a `CHECK (student_id_a < student_id_b)` and `UNIQUE (student_id_a, student_id_b)` that together make each pair canonical regardless of insertion order, which is what lets `create_separation_handler` be idempotent (re-adding a pair in either order returns the existing row via `ON CONFLICT DO NOTHING` + a follow-up `SELECT`, rather than erroring).

### Frontend (`app/`)

- Routes are declared explicitly in `app/routes.ts` using `@react-router/dev/routes` helpers (`index`, `route`, `layout`, `prefix`) — this is the single source of truth for the route tree, not filesystem-based routing. When adding a page, add its entry here. `/login`, `/signup`, and the three `api/*` routes (`api/student-image-upload`, `api/student-image`, `api/quick-search`) sit outside `app-shell.tsx` and render/respond standalone; every other page is nested under `layout("layouts/app-shell.tsx", [...])`. Within that, the `students` and `classrooms` route groups are further wrapped in their own `layout()` (`app/layouts/students.tsx`, `app/layouts/classrooms.tsx`) — `layout()` adds a nesting level without changing the URL. Beyond a shared `ErrorBoundary` (see below), the students layout also renders the scrollable `h-full min-h-0 overflow-y-auto` wrapper the students index page relies on; both group layouts additionally set `requireAuth` as their `middleware` (see below), gating that whole subtree — `/` (`home.tsx`) is the one page left intentionally public.
- Each route file under `app/routes/{students,classrooms}/` typically exports a `loader` (GET data, used by index/detail pages) and/or an `action` (form POST/DELETE mutations, used by create/delete pages), following React Router's data APIs. React Router's Vite plugin strips `loader`/`action` exports out of the client bundle for every route *except* the one currently rendering — importing another route's `action` as a value (e.g. to type a `useFetcher` submitting to it) must use `import type { action as ... } from "./other-route"`, not a plain value import, or the client bundle throws `does not provide an export named 'action'` at runtime. This applies even to a route's *own* action when the `useFetcher` call lives outside the route file itself — e.g. `classroom-seating-chart.tsx`'s `action` is only invoked by `SeatingChartCanvas`, which does `useFetcher<typeof classroomAction>()` against a type-only import of it (see below).
- `app/lib/api.ts` holds typed fetch wrappers for every backend call (`getStudent(s)`/`getStudentsPage`/`getStudentLimitStatus`, `create/update/deleteStudent`, `bulkDeleteStudents`, `getClassroom(s)`, `create/update/deleteClassroom`, `getClassroomSeatingChart`, `updateClassroomSeatingChart`, `generateRandomSeatingChart`, `pickColdCallStudent`, `getSeparations`/`createSeparation`/`deleteSeparation`) — all routes go through it; there are no inline `fetch("http://localhost:3001/...")` calls left in route files, and there is no tables/seats-specific fetch wrapper since those aren't separately addressable (see Backend section above). Extend `api.ts` rather than adding an inline fetch.
- `app/lib/schemas.ts` defines zod schemas per resource (`Create*Schema`/`Update*Schema`, plus `SeatingChartSchema`, `CreateSeparationSchema`) used both for frontend form validation and as the `z.infer<...>` types passed to `api.ts`'s mutation functions — `Student`, `Classroom`, `SeatingChart`, `ColdCall`(`Pick`), and `Separation` are all `z.infer<>` types exported from here, not `types.ts` (see below).
- `app/lib/auth.ts` has the two Clerk helpers routes use: `requireAuth` (a `middleware` export that redirects to `/login` if unauthenticated — set per route-group, see above) and `tokenFromRequest` (best-effort token lookup for mutation-only routes, where the backend's own 401 is the source of truth). `getToken()`'s result is threaded through as a Bearer token to every `api.ts` call. `/login`/`/signup` (`app/routes/auth/`) render Clerk's own sign-in/sign-up UI standalone, outside `app-shell`.
- Student photos go through the Rust backend, not a Node route: `POST /api/v1/students/image-upload-url` (`create_student_image_upload_url_handler`) issues a presigned PUT URL against a real Cloudflare R2 bucket (a dedicated bucket per environment — no MinIO, including locally), the browser PUTs the file straight to the bucket, and only the resulting `image_url` is saved via the normal student create/update call; `GET /api/v1/students/{id}/image` (`get_student_image_handler`) streams the photo back with an ownership check. `app/hooks/use-student-image.ts` fetches through this authenticated proxy (a bare `<img src>` can't carry the Bearer token an R2-direct URL would need). `student-avatar.tsx`/`student-photo-field.tsx` are the display/upload UI.
- `app/routes/classrooms/cold-call.tsx` drives the cold-call picker against `POST .../cold-call` (`src/cold_call.rs` on the backend, see above); per-student weights are ephemeral component state for that session, never persisted.
- `app/routes/api/quick-search.tsx` (backing `topbar-search.tsx`) looks up students by name via `getStudentsPage`, capped to 5 results; used for the topbar's global search.
- `app/lib/types.ts` defines frontend-side `Table`/`Seat` types independently from the Rust models/schemas (see note in Project overview above about keeping these in sync); `Table` is only actually consumed via `createCanvasTable`'s return value (see below), not threaded further into the canvas itself. `Student`/`Classroom` and every other API-backed type live in `schemas.ts` instead (see above) — `types.ts` is only for shapes with no corresponding zod schema.
- UI components in `app/components/ui/` are shadcn-generated (style `base-rhea`, Tailwind v4, path aliases configured in `components.json` — `~/components`, `~/lib`, `~/hooks`, etc., matching the `~/*` → `./app/*` tsconfig path). Use the shadcn CLI conventions (Base UI primitives via `render` prop, e.g. `<Button render={<Link .../>} />`) rather than hand-rolling new primitives. `app/components/base-node.tsx`, `base-handle.tsx`, and `labeled-handle.tsx` (flat under `app/components/`, not moved alongside the seating-chart component split below) are the analogous scaffold for the React Flow canvas (from the React Flow component registry, not shadcn) — leave these alone the same way you would shadcn output, even if a given prop/export looks unused. `DialogContent` (`ui/dialog.tsx`) portals its children outside the triggering DOM subtree — a `<form>` around a dialog's fields/submit button must live *inside* `DialogContent`, not wrap it, or the submit button ends up outside the form in the DOM and `onSubmit` silently never fires.
- The seating-chart canvas's own components live under `app/components/seating-chart/` (`seating-chart-canvas.tsx`, `boundary-node.tsx`, `table-node.tsx`, `seat-node.tsx`, `student-node.tsx`, `seating-chart-dialogs.tsx`, `seating-chart-roster.tsx`, `student-card-content.tsx`) rather than flat under `app/components/`. `context.ts` here exports a plain `LockedContext` (`createContext(false)`) carrying the canvas's locked/edit-mode flag down to `student-node.tsx`, instead of prop-drilling it. `app/components/classroom/` holds the per-tab components described below (`overview-tab.tsx`, `roster-tab.tsx`, `cold-call-tab.tsx`, plus `add-students-dialog.tsx`, `seating-chart-preview.tsx`, `seating-preferences-dialog.tsx`, `unsaved-chart-changes-dialog.tsx`).
- `app/root.tsx` defines the document `Layout`, a `HydrateFallback` spinner, and a top-level `Card`-styled `ErrorBoundary` (the last-resort fallback when no nested route boundary catches the error — see below). Theme switching is fully wired via `next-themes`: `root.tsx`'s `Layout` wraps the app in `next-themes`' own `ThemeProvider` (`attribute="class"`, `defaultTheme="light"`, `storageKey="vite-ui-theme"`), and `theme-toggle.tsx` reads/writes it via `next-themes`' `useTheme` — the anti-flash pre-hydration script is injected automatically by `next-themes` itself rather than hand-rolled. `NeonAuthUIProvider` (see Neon Auth below) also wraps its children in its own `next-themes` `ThemeProvider`, but `next-themes` detects the ancestor context from `root.tsx` and no-ops that inner instance rather than double-managing the theme — this is why `root.tsx`'s provider must come from `next-themes` itself, not a separate implementation, and why it must render above `NeonAuthUIProvider` in the tree. Don't wire a `loader`-based theme cookie into `theme-toggle.tsx` — `useRouteLoaderData("root")` is always `undefined` since `root.tsx` has no `loader`. The root layout (`App`) wraps everything in `ClerkProvider`/`TooltipProvider` plus a bare `h-dvh overflow-hidden flex-col` div around `Outlet` — it renders no nav of its own. `app-shell.tsx` (the `layout()` route described above) is where persistent chrome (`AppTopbar`/`AppSidebar`, via shadcn's `Sidebar` primitives) and the full-height flex chain actually start: `SidebarProvider`/`SidebarInset` continue it as `min-h-0 flex-1` so pages needing full-height layout (like the seating chart) can stretch to the bottom of the window without a page-level scrollbar. Extend that `flex-1 min-h-0` chain (it must be unbroken at every nesting level, since a flex item's default `min-height: auto` otherwise lets its content force it taller than available space) rather than introducing a second height strategy; in particular, don't reach for a viewport-relative height like `min-h-svh`/`h-screen` on a routed page — it assumes the element owns the full screen height, but nested inside that chain it ends up taller than its actual container, breaking things like `justify-center` centering against the wrong height. Use `h-full` instead.
- Route-level `ErrorBoundary`s render a shared `RouteErrorCard` (`app/components/route-error-card.tsx`) — a `Card`-styled fallback taking `error`/`title`/`fallbackDetails`/`backTo`/`backLabel` props — reused by `app/layouts/students.tsx` and `app/layouts/classrooms.tsx`. Reuse it for any new route-group `ErrorBoundary` rather than hand-rolling another error card. React Router renders the nearest ancestor route's `ErrorBoundary` in place of *that entire route segment's output* (not just its `Outlet`), so a boundary defined on a layout route replaces that layout's own UI too — e.g. the students layout's `ErrorBoundary` also replaces its scrollable wrapper div, not just the routed content. Only routes above the boundary in the tree survive (`app-shell.tsx`'s `AppTopbar`/`AppSidebar` always do, since it's an ancestor of both group layouts); getting a section's persistent chrome to survive its own errors would require a deeper layout split, which hasn't been done here.
- The classroom detail page is a parent/child route split, not one file. `app/routes/classrooms/classroom.tsx` (route id `"classroom"` — see `routes.ts`) owns the shared `loader` (classroom, students, seating chart, separations, all fetched in parallel) plus static page chrome (period/subject/term header, pin toggle) and a tab nav (`app/lib/classroom-tabs.ts`'s `ClassroomTab`/`classroomTabFromPathname`, driven off `useLocation()` since Base UI's `Tabs.Tab` can't be used here — looping infinitely when composed with a `Link` `render` prop); it renders an `<Outlet>` for four child routes: `classroom-overview.tsx`, `classroom-roster.tsx`, `classroom-seating-chart.tsx`, `cold-call.tsx`. Each child route is itself a thin file that reads the parent's loader data via `useClassroomData()` (`app/lib/classroom-route-data.ts`, a typed wrapper around `useRouteLoaderData` keyed on the `"classroom"` route id) and renders one `app/components/classroom/*-tab.tsx` component. Cold-call weights are lifted into `classroom.tsx` itself (not the cold-call tab) as `ClassroomOutletContext`, passed through `<Outlet context={...}>`, so they survive navigating away from and back to that tab (the layout route doesn't unmount across child navigations). `classroom.tsx` also exports a `handle: BreadcrumbHandle` (`app/lib/breadcrumb.ts`) for the topbar breadcrumb — note `BreadcrumbHandle.to`'s doc comment: a pathless layout route's own `useMatches()` pathname isn't reliable (it resolves to the parent's), so `to` takes an explicit path/function rather than reading it off the match.
- `classroom-seating-chart.tsx` is what renders `SeatingChartCanvas` (`app/components/seating-chart/seating-chart-canvas.tsx`) with `classroomId`/`seatingChart`/`students` from `useClassroomData()`, and owns the seating-chart `PUT` `action` — the `useFetcher<typeof classroomAction>()` type-only-import gotcha described above now applies to *this* file's `action`, not `classroom.tsx`'s. `SeatingChartCanvas` (a thin `ReactFlowProvider` wrapper around the real implementation, `SeatingChartEditor`) is the entire interactive seating chart on **React Flow** (`@xyflow/react`): the toolbar (Edit Chart/Cancel/Save), the "..." dropdown (Add Table/Randomize/Boundary Size/Unassign All — the earlier still-unwired Edit Classroom/Manage Students/Delete Classroom stubs are gone; classroom editing and the roster now live on their own tabs, see below), the three dialogs (imported from `app/components/seating-chart/seating-chart-dialogs.tsx` — `RandomSeatingChartDialog`, `BoundarySizeDialog`, `UnassignAllDialog`), the roster panel (`RosterPanel`, `app/components/seating-chart/seating-chart-roster.tsx`), and the canvas itself all live in this one component, along with every piece of state that drives them (`nodes`, `locked`, the three dialog-open flags, the save `fetcher`). Boundary, tables, seats, and students are all React Flow nodes (`type: "boundary" | "table" | "seat" | "student"`, see `nodeTypes` in `seating-chart-canvas.tsx`, rendered by `app/components/seating-chart/boundary-node.tsx` / `table-node.tsx` / `seat-node.tsx` / `student-node.tsx`); there are no `Edge`s at all. A seat assignment is modeled purely by a student node's `parentId` pointing at a seat node's id (`parentId` unset means the student is unassigned/floating on the canvas); a seat node is itself parented to its table via its own `parentId`. `useNodesState` (React Flow's own hook, driving `onNodesChange`) holds all of this — including the boundary — directly as one array (no reducer, no separate state channel for the boundary); `SeatingChartEditor` builds the initial nodes once via `buildInitialNodes` (memoized with an empty dep array — deliberately not reactive to prop changes after mount), and `Save` calls `buildSeatingChartPayload` to convert nodes back into a `SeatingChartSchema` payload (tables *and* the boundary node's dimensions) and submits it in one `PUT` via `useFetcher`, using `fetcher.state`/`fetcher.data` to drive the Save button's disabled/spinner state and an inline save-error message.
- The seating chart's boundary (its canvas rectangle) is a single, real `"boundary"` node (id `BOUNDARY_NODE_ID`, `app/components/seating-chart/boundary-node.tsx`) built by `buildBoundaryNode`/`buildInitialNodes` alongside the table/seat/student nodes, and updated the same way they are — via `setNodes`. `getBoundary(nodes)` (`seating-chart-utils.ts`) reads the current `{width, height}` back out of `nodes` wherever it's needed, rather than a separate context (e.g. `table-node.tsx`'s row/column-grow handlers call `getBoundary(getNodes())`). `reorderNodes` keeps the boundary node first, ahead of table/seat/student nodes, whenever it re-sorts state. Each table node carries its own `extent`, computed via `tableExtent(boundary)` and clamped to `[[0, 0], [boundary.width, boundary.height]]`, which is what stops a table from being dragged outside the boundary; `extent` is set at every point a table node is constructed or the boundary changes (`buildInitialNodes`, `SeatingChartEditor`'s `handleAddTable`/`handleBoundarySave`) rather than recomputed on every render. Editing the boundary size (`BoundarySizeDialog`, rendered from `SeatingChartEditor`) updates the boundary node and every table's `extent` in one `setNodes` call; `getBoundaryMinSize` (`seating-chart-utils.ts`) computes the smallest boundary that still fits all existing tables, used to floor the dialog's width/height inputs so shrinking can't strand a table outside the new boundary. Student nodes get a looser `extent` than tables — `canvasExtent(boundary)` (`seating-chart-utils.ts`), the boundary padded by `CANVAS_PADDING` on every side — since a student (unlike a table) is allowed to float outside the strict boundary once placed; it's set at every point a student node is constructed (`buildInitialNodes`, `SeatingChartEditor`'s `handleDragEnd` for a roster drop) and kept in sync in `handleBoundarySave`, same as tables. `SeatingChartEditor`'s `canvasArea` (also used as the pane's `translateExtent`) is just this same `canvasExtent(boundary)`.
- `SeatingChartEditor` reframes the viewport on the boundary via `useReactFlow().fitView({ nodes: [{ id: BOUNDARY_NODE_ID }] })` — once in a mount-only `useEffect`, and again inline at the end of every handler that replaces the boundary wholesale (`handleCancel`, `handleBoundarySave`, `handleRandomize`), right after the triggering `setNodes` call. Scoping to `{ id: BOUNDARY_NODE_ID }` (rather than a bare `fitView()`) frames exactly the boundary rect — a bare `fitView()` would also pull in any floating student positioned outside it. Known low-severity gotcha: `fitView` prefers a node's async-updated `measured` size over its explicit `width`/`height`, so calling it same-tick as a resize can frame the previous size for one frame; no glitch seen in practice, but wrap in `requestAnimationFrame` if one turns up.
- Student/classroom create and edit are no longer dedicated pages — `create-student.tsx`/`edit-student.tsx`/`create-classroom.tsx`/`edit-classroom.tsx` still exist as route files (for their `loader`/`action` only) but render `<Navigate to="/students" replace />` (or `/classrooms`) if hit directly, since a bookmark/refresh would otherwise show a blank content area. The real UI is `StudentFormDialog`/`ClassroomFormDialog` (`app/components/student-form-dialog.tsx`/`classroom-form-dialog.tsx`), opened from many places (topbar, sidebar, home pages, roster tab, table columns) and backed by the shared `useResourceFormDialog` hook (`app/hooks/use-resource-form-dialog.ts` — see above): it owns open state, resets the caller's `react-hook-form` instance on open (the dialog stays permanently mounted, so stale state must be cleared each time), submits via `useFetcher().submit(payload, { method: "post", action: actionPath, encType: "application/json" })` against the route's `action`, and on success shows a toast and closes. In edit mode, `buildSubmitData` filters the payload down to only `dirtyFields` rather than resubmitting the whole form. Delete confirmations follow the analogous `useDeleteResource` hook (`app/hooks/use-delete-resource.ts`) + shared `DeleteConfirmDialog` (`app/components/delete-confirm-dialog.tsx`) pair — `DeleteStudentDialog`/`DeleteClassroomDialog` wrap them per-resource, submitting to that row's own `/…/delete` path via `fetcher.submit`, with an `onlyIfViewing` option so a delete triggered from the resource's own detail page navigates away on success but one triggered from a list page doesn't. Delete actions (`delete-student.tsx`/`delete-classroom.tsx`) let a failed API call propagate rather than swallowing it — an error there is meant to surface through the nearest `ErrorBoundary` (see above), not silently redirect as if it succeeded.
- Each table has a `rows`/`cols` grid shape (`TableNodeData`, capped at `MAX_TABLE_DIMENSION` each) rather than a fixed seat count; a seat's identity is its `(row, col)` coordinate (`SeatNodeData`, seat id from `getSeatId(tableId, row, col)`), not a flat index — growing/shrinking one dimension only adds/removes the seats on that outer edge, so existing occupants never get reshuffled. `getSeatPosition(row, col)` and `getTableNodeSize(rows, cols)` derive pixel position/size from a fixed per-seat cell size, so a table grows physically bigger as rows/cols increase rather than shrinking its seats to fit. `TableNode` renders a `NodeToolbar` with row/column +/- steppers and the table's delete button, relying on `NodeToolbar`'s own default visibility (shown only when its node is selected) rather than a manual `isVisible` check — this is safe because `elementsSelectable={!locked}` (`seating-chart-canvas.tsx`) already prevents selecting a node while the chart is locked, and both `Save`/`Cancel` explicitly clear selection before re-locking. All the toolbar's handlers mutate canvas state via `useReactFlow().setNodes()` directly from within the node component — this is the pattern to follow for any other per-node action button, rather than threading callbacks through props.
- All of this pure, framework-free geometry/id logic (constants like `GRID_STEP`/`SEAT_NODE_SIZE`/`MAX_TABLE_DIMENSION`, node shape types, `buildInitialNodes`, `buildSeatingChartPayload`, `getSeatPosition`/`getTableNodeSize`, seat-id helpers) lives in `app/lib/seating-chart-utils.ts`, tested directly in `app/lib/seating-chart-utils.test.ts` — this is the template for any other local, non-persisted-shape UI logic: keep it out of components and out of `api.ts`/`types.ts` (which model actual API-backed shapes).
- Drag/drop uses React Flow's `getIntersectingNodes` for exact overlap hit-testing (not a distance/proximity threshold): dragging a student node over an unoccupied seat highlights it (`highlight`/`highlight-rejected` className depending on whether the seat is already occupied) and drops it onto that seat on drag-stop by setting `parentId`; dragging a seated student off any seat clears its `parentId` back to `undefined`, positioning it at its last absolute canvas position via `getInternalNode`. The roster panel's unassigned students use `@dnd-kit/core` (`DndContext`/`useDraggable`/`useDroppable`/`DragOverlay`, plus `@dnd-kit/utilities`'s `CSS` transform helper) rather than native HTML5 drag-and-drop, since touch browsers never fire HTML5 DnD events at all — a single `PointerSensor` with a delay/tolerance activation constraint (not a distance constraint, which can't distinguish a scroll-swipe from drag-intent on touch) lets a quick swipe still scroll the roster's `ScrollArea` while a press-and-hold starts a drag. `DndContext`'s `onDragEnd` reconstructs the drop's screen coordinates from `event.activatorEvent`'s `clientX`/`clientY` plus `event.delta`, then feeds them through the same `screenToFlowPosition`/`getIntersectingNodes` rectangle test described above, landing the new student on a seat if dropped on one or floating freely otherwise; the canvas wrapper is the sole `useDroppable` target (via `CANVAS_DROPPABLE_ID`), wrapped in its own small `CanvasDropZone` component rather than calling `useDroppable` directly inside `SeatingChartEditor` — `useDroppable`/`useDraggable` only see the real `DndContext` instance when called from a component that renders as `DndContext`'s *descendant*, not from the same component whose return value constructs the `<DndContext>` element itself; getting this wrong silently no-ops the drop (the draggable half still animates and fires `onDragStart`, making it look like it's working) rather than throwing, so it's easy to miss. `DndContext` also sets `autoScroll={false}`: the chip drag originates inside the roster's small `ScrollArea`, and dnd-kit's default auto-scroll otherwise tries to scroll that container toward the pointer as it moves onto the canvas, corrupting the computed drop delta. The dragged chip's preview renders via `DragOverlay`, which portals to `document.body` so it isn't clipped by the roster's `ScrollArea` overflow.
- `app/hooks/` also has `useClassroomPatch` (`use-classroom-patch.ts`), the base every classroom `PATCH` goes through (form edits via `useResourceFormDialog` above, *and* pin/unpin) — it submits to the existing `/classrooms/{id}/edit` action rather than a dedicated per-field route, expecting `MutationResult` (`app/lib/action-results.ts`, a 2-line `{ok:true}|{ok:false,error}` discriminated union — the shared fetcher-data shape both this and `useResourceFormDialog`/`useDeleteResource` above expect). `usePinClassroom` (`use-pin-classroom.ts`, used by `PinToggleButton`) is a thin wrapper over it that also toast-blocks a new pin once `isAtPinLimit` (`classroom-limit.ts`) is true.
- Student separations ("keep these two students apart") are edited via `SeatingPreferencesDialog` (`app/components/classroom/seating-preferences-dialog.tsx` — despite the name, it edits both a student's front/back seating preference *and* their separations in one dialog, via a `Combobox` multi-select against the rest of the roster) and surfaced as a `SeparationAvoidBadge` on each roster row (`roster-tab.tsx`). `Separation`'s `student_id_a`/`student_id_b` pair is unordered from the frontend's perspective — `roster-tab.tsx` builds a `studentsById`-keyed lookup off the full `separations` list (passed down from `classroom.tsx`'s loader) to resolve "who is this student avoided by" in either direction, rather than assuming a fixed order.
- The students index page (`student-home.tsx`) paginates server-side via `getStudentsPage` (`page`/`q`/`sort_by`/`sort_dir` query params, mirrored in `student_list_handler`'s `QueryBuilder` above) and renders `getPageNumbers` (`app/lib/pagination.ts`)'s ellipsis-collapsed page list. It also has a grid/table view toggle: table view is `@tanstack/react-table` (`useReactTable`, `flexRender`, `RowSelectionState` for bulk-select — feeding `bulkDeleteStudents`/the `bulk-unassign-students.tsx` action), and the chosen view persists via `useStudentViewMode` (`app/hooks/use-student-view-mode.ts`) writing a cookie (`app/lib/view-mode-cookie.ts`, `students-view-mode`, 1yr) so the SSR loader can render the right layout on first paint instead of flashing the wrong one.

## Testing

### Backend (`src/handlers/*.rs`)

- Tests are colocated `#[cfg(test)] mod tests` blocks at the bottom of each handler file. The crate is a library (`src/lib.rs`) with two thin binaries (`src/main.rs` for local dev/docker-compose, `api/index.rs` for Vercel Functions); handler code and `#[cfg(test)] mod test_support` live under the lib, so tests still see private items like `AppState.db` the same way they would in a binary-only crate — same-crate visibility, not same-file.
- Each test is a plain `#[tokio::test] async fn x() -> anyhow::Result<()>` that opens `crate::test_support::TestDb::new().await` (creates a uniquely-named database, runs `supabase/migrations/*.sql` into it via `client.batch_execute`, `DROP DATABASE`s it on `Drop`), then `let pool = __tdb.pool();` and drives the real `Router` (from `routes::create_router`) via `tower::ServiceExt::oneshot`. This replaces the old `#[sqlx::test]`. Dev-dependencies: `anyhow`, `tower` (`util` feature), `http-body-util`.
- Seed/assert helpers in each handler's `mod tests` go through `test_support`'s `seed_one` / `seed_opt` / `seed_all` / `seed_scalar` / `seed_exec` — `#[cfg(test)]`-only unwrapping wrappers that call `conn.query_typed*` / `execute_typed` directly, taking `&crate::db::Db` + `&[(&(dyn ToSql + Sync), Type)]`.
- `src/test_support.rs` builds the router with `jwks_verifier: None` (real JWT/JWKS verification is bypassed) and provides `authenticated_request`/`authenticated_json_request`, which attach a hand-built `SupabaseAuthClaims` extension for a given `user_id` — every handler's own auth-extraction and user-scoping logic still runs. `test_user_id()` mints a fresh id per test. `app_with_blob_deleter(pool, deleter)` swaps in a test `BlobDeleter` (e.g. `RecordingBlobDeleter`) for asserting on photo-cleanup calls.
- Running tests needs a Postgres reachable via `POSTGRES_URL` where the test user can `CREATE DATABASE` — the local Supabase db (`127.0.0.1:54322`) locally, an ephemeral `postgres:18` service in CI. `TestDb` migrates each per-test database itself; there is no separate migration step.

### Frontend (`app/routes/**/*.test.ts`)

- Vitest, configured via a dedicated `vitest.config.ts` at the repo root rather than extending `vite.config.ts` (whose `reactRouter()` plugin does SSR/route-manifest work that isn't needed for plain function tests), plus `vite-tsconfig-paths` for the `~/*` alias.
- Scope is route loader/action logic and colocated pure state modules — not component rendering — no `@testing-library/react`, `jsdom`, or MSW (`vitest.config.ts` uses `environment: "node"`). Route tests call the exported `action`/`loader` functions directly with a constructed `Request`/`params`, mocking `fetch` via `vi.stubGlobal("fetch", vi.fn())` and resolving real `Response` objects (matches `api.ts`'s `response.ok`/`.json()` usage); for a `loader` made of parallel fetches (e.g. `Promise.all([...])`), `mockResolvedValueOnce` calls queue in *call order*, which is deterministic even though the underlying promises resolve out of order.
- Non-route pure-logic modules (e.g. `seating-chart-utils.ts`'s node/geometry helpers) are tested directly as plain functions — no fetch mocking or route-args scaffolding needed, just call them.
- Colocated as `*.test.ts` next to the file under test, e.g. `app/routes/students/create-student.test.ts` (action), `app/routes/classrooms/classroom.test.ts` (loader), `app/lib/seating-chart-utils.test.ts` (pure geometry/node-building helpers).

### End-to-end (Playwright)

- `tests/e2e/*.spec.ts`, run via `npm run test:e2e`. Requires the dev stack (frontend + backend + Postgres) already running — `playwright.config.ts` does not auto-start it. Uses `@clerk/testing` for real sign-in flows; not currently wired into CI (see below), so run it manually before relying on it.

## CI (`.github/workflows/`)

- `node.js.yml`: `npm ci` + `npm run build --if-present` + `npm test`, on Node 22.x and 26.x.
- `rust.yml`: two jobs. `test` spins up an ephemeral `postgres:18` service and runs `cargo test --all-features` (the `TestDb` harness creates + migrates a database per test — no separate migration step). `formatting` needs **no** database (no compile-time DB anymore) — it runs `rustfmt` check + `cargo clippy --all-targets -- -D warnings`. `node.js.yml`/`rust.yml` are required status checks on `main` (branch protection) — there is no separate gated deploy workflow, since deployment is Vercel's own native Git integration (auto preview-deploy per PR, auto production-deploy on merge to `main`), not anything defined in this repo.
- `release.yml`: triggered on pushing a `v*` tag (not on `main` pushes or PRs). It checks out the tagged commit, fails if the tag doesn't match `Cargo.toml`/`package.json` versions, then runs `gh release create` with `--generate-notes` (categorized via `.github/release.yml`), auto-marking it `--prerelease` when the tag has a hyphen (`v0.2.0-beta.2`) and `--latest` otherwise. It's idempotent — a re-run against an existing release no-ops. The release flow: branch `release/vX` off `main`, run `scripts/bump-version.sh X` (bumps `package.json`/`package-lock.json` via npm and the `class_management` entry in `Cargo.toml`/`Cargo.lock`), commit as `chore(release): vX`, PR to `main`, merge, then `git tag vX <merge-sha> && git push origin vX`. Vercel still deploys off the `main` merge itself; the tag/release is a marker, not a deploy gate.
- CI never touches the real Supabase database. There is no GitHub Actions or Vercel-build migration step: `supabase/migrations/*.sql` is applied to the real `development`/Preview/Production databases out-of-band via the Supabase CLI (`npx supabase db push`), the dashboard SQL editor, or the Supabase MCP `apply_migration`. Apply new migrations there before (or as part of) the PR that needs them.
